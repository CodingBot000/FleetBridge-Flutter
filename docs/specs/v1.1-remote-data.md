# v1.1 Remote Data Source

v1.0 로컬 시뮬레이터를 유지하면서 로컬 Mock REST API를 선택할 수 있도록 데이터 계층을 확장합니다. 기존 FleetBridge 저장소와 v1.0 Release·태그는 변경하지 않습니다. 유료 서비스나 외부 관제 서버를 사용하지 않습니다.

## 데이터와 화면의 책임

UI는 `VehicleStore` 인터페이스를 사용합니다. `VehicleRepository`는 기존 로컬 시뮬레이션을 담당하고, `RemoteVehicleStore`는 서버 스냅샷을 저장합니다. Riverpod Provider는 선택한 저장소를 생성·해제하고 `ListenableBuilder`는 변경을 구독합니다.

Remote 모드는 처음에 빈 상태로 시작하며 목록과 상세를 HTTP로 가져옵니다. 서버만 위치·상태·배터리·냉동기 상태를 변경합니다. 앱은 5초마다 목록을 조회하고 revision이 높은 스냅샷만 반영합니다. 조회 실패 시 마지막 데이터와 오류를 함께 표시하며 로컬 데이터로 대체하지 않습니다. 백그라운드에서 폴링을 중단하고 목록·차량별 상세 요청의 소유권을 무효화합니다. 복귀하면 이전 요청 완료를 기다리지 않고 새 조회를 시작합니다. 현재 요청 객체와 동일한 응답만 데이터·로딩·오류에 반영하며, 동일 세대의 중복 목록·상세 조회는 하나의 Future를 공유합니다. 목록 오류와 차량별 상세 오류는 각각 성공한 조회에서만 지웁니다. HTTP Client와 요청 ID 생성기는 주입할 수 있습니다.

## 승인된 명령 정책 (2026-11-16)

사용자가 다음 정책을 승인했습니다.

- 요청 ID·요청 내용·결과는 서버 프로세스 메모리에 서버 종료까지 보관합니다. 재시작하면 초기화됩니다.
- 같은 ID·같은 요청은 처리 중 상태 또는 기존 결과를 반환하며 명령을 다시 실행하지 않습니다. 같은 ID에 다른 내용이 오면 HTTP 409로 거부합니다.
- 처리 중인 차량에 다른 요청 ID로 명령을 보내도 409로 거부합니다.
- 클라이언트 타임아웃은 명령 실패 확정이 아닙니다. ‘결과 확인 필요’로 표시하며 자동 POST 재전송을 하지 않습니다.
- 결과가 불명확한 동안 해당 차량의 새 명령을 차단하고, 사용자가 기존 요청 ID로 결과를 조회해 성공·실패가 확인되어야 차단을 해제합니다. 조회 실패·pending·404는 차단을 유지합니다.

클라이언트가 연결을 끊어도 서버의 명령 처리는 계속됩니다. 명령 시나리오 `timeout`은 Remote에서 4초 후 성공하는 지연 응답으로 사용합니다. 앱의 HTTP 대기 제한은 2초이므로 결과 확인 흐름을 재현할 수 있습니다. Local에서는 기존 3초 후 모의 timeout 결과를 유지합니다. 이 시간과 5초 폴링은 개발 시나리오를 위한 구현값이며 운영 SLA나 용량 정책이 아닙니다.

## API

Python 표준 라이브러리 `ThreadingHTTPServer`로 구현합니다. 기본 바인딩은 `127.0.0.1:8080`이며 인증 없는 로컬 개발 전용입니다. 외부 네트워크에 노출하지 않습니다.

| 요청 | 응답 |
| --- | --- |
| `GET /vehicles` | 차량 배열. ID·이름·모델·좌표·상태·배터리·UTC 시각·냉동기·revision |
| `GET /vehicles/{id}` | 차량 하나, 없는 차량은 404 |
| `POST /commands` | `requestId`, `vehicleId`, `enabled`, `scenario`를 받고 명령 실행 또는 기존 결과 반환 |
| `GET /commands/{requestId}` | `requestId`, 원본 payload, `result: pending/success/failure`. 기록이 없으면 404 |

입력 오류는 400, 같은 ID의 내용 충돌·동일 차량 처리 중은 409, 없는 차량·오프라인 차량 명령은 422입니다. 명령 failure 시나리오는 정상 JSON 응답의 `result: failure`로 반환합니다. 5xx·통신 오류·잘못된 명령 응답은 처리 여부를 알 수 없으므로 클라이언트에서 결과 불명확으로 다룹니다. JSON 변환은 필드 타입·상태·좌표·배터리·revision·ID를 검사합니다. 명령 응답은 요청 ID와 vehicleId·enabled·scenario가 모두 원본 요청과 일치해야 인정합니다. POST의 400/409/422도 명세의 거부 error 코드가 함께 있어야 실패 확정으로 처리하며, 잘못된 JSON이나 알 수 없는 error 코드는 불명확 상태로 남깁니다. 결과 조회의 모든 HTTP 오류는 차단을 유지합니다.

## 비동기 상태와 서버 잠금

목록 조회와 각 차량 상세 조회는 각각 요청 객체를 등록한 뒤 알립니다. 따라서 알림을 받은 코드가 즉시 재조회해도 중복 요청을 만들지 않습니다. `stop()`에서 기존 요청을 무효화하면 이전 응답이나 finally는 새 요청의 로딩·오류를 변경하지 못합니다. 실제 소켓을 stop 시점에 강제 취소하는 방식은 아니며, HTTP Future의 대기 제한과 dispose 시 Client 종료를 사용합니다.

명령 성공 직전에 시작된 목록 요청은 명령 반영을 보장하지 못하므로 성공 응답·결과 조회 후 새 목록 요청을 시작합니다. 목록·상세 사이의 도착 순서는 차량 revision으로 방어합니다. 명령은 화면보다 저장소가 오래 소유하므로 화면 종료·재진입에도 요청 ID와 결과 확인 차단을 유지합니다.

서버는 요청 ID 등록과 차량별 pending 검사를 하나의 잠금 안에서 수행합니다. 응답 데이터는 잠금 안에서 복사하고 네트워크 쓰기는 잠금을 해제한 뒤 실행합니다. 클라이언트 연결 종료는 이미 접수한 명령을 취소하지 않습니다. 테스트에서는 명령 지연 함수를 Event로 제어해 동시 요청과 단일 실행을 검증합니다.

## 실행

```sh
python3 mock_server/server.py --port 8080
```

다른 터미널에서 실행합니다. 기본 모드는 Local입니다.

```sh
flutter pub get --enforce-lockfile
flutter devices
flutter run -d <device-id> --dart-define=FLEET_MODE=local
flutter run -d <device-id> --dart-define=FLEET_MODE=remote
```

Remote 기본 주소는 iOS Simulator에서 `http://127.0.0.1:8080`, Android Emulator에서 호스트 루프백을 가리키는 `http://10.0.2.2:8080`입니다. 다음 개발 설정으로 주소를 바꿀 수 있습니다.

```sh
flutter run -d <device-id> --dart-define=FLEET_MODE=remote \
  --dart-define=FLEET_API_URL=http://127.0.0.1:8080
```

Android는 debug manifest에서만 cleartext HTTP를 허용합니다. iOS는 로컬 네트워크 접근을 허용합니다. 외부 API·배포용 HTTP 보안 설정을 제공하는 것은 아닙니다.

실제 HTTP 테스트는 `--no-ticks`로 서버의 자동 시뮬레이션 갱신을 끕니다. 명령 revision 검사가 테스트 실행 속도에 영향을 받지 않게 하기 위한 옵션이며 일반 실행은 5초 갱신을 유지합니다.

## 장애 재현

실행 중인 서버를 종료하면 앱의 조회 오류와 마지막 스냅샷 유지를 확인할 수 있습니다. 아래 명령은 별도 서버 실행 예입니다. 같은 포트의 기존 서버를 먼저 종료합니다.

```sh
# GET 응답을 3초 늦춰 조회 타임아웃 재현
python3 mock_server/server.py --read-delay 3
# GET 응답에 HTTP 503 반환
python3 mock_server/server.py --read-error
```

명령 응답 지연은 화면의 시간 초과 시나리오를 선택합니다. POST는 한 번만 전송되며 서버가 나중에 완료한 결과를 ‘명령 결과 조회’로 확인합니다. 조회용 장애 옵션은 명령 결과 조회에도 적용되므로 오류 중에는 차단이 유지됩니다.

## 검증 방법과 한계

```sh
flutter analyze
flutter test
python3 -m unittest discover -s mock_server -v

# 서버를 실행한 상태에서 Android 화면 검증·스크린샷
flutter drive --driver=test_driver/integration_test.dart \
  --target=integration_test/remote_device_test.dart -d <android-device-id> \
  --dart-define=FLEET_MODE=remote

# iOS Simulator 화면 검증
flutter test integration_test/remote_device_test.dart -d <ios-simulator-id> \
  --dart-define=FLEET_MODE=remote
```

[VehicleApi 테스트](../../test/vehicle_api_test.dart)는 주입한 Client로 JSON·오류·타임아웃을 검사합니다. [실제 HTTP 테스트](../../test/remote_http_test.dart)는 별도 Python 프로세스를 띄워 Dart 앱 계층에서 소켓 통신, 불명확 상태, 새 명령 차단, 결과 확인과 서버 연결 종료를 검사합니다. [저장소 테스트](../../test/remote_store_test.dart)는 404 시 차단 유지, 자동 재전송 없음, 오래된 revision 거부, 조회 실패·복구, 해제 후 응답 무시를 확인합니다. Python 테스트는 중복·충돌·지연 후 완료·오프라인·503을 검증합니다. CI는 Flutter 분석·테스트와 Python HTTP 테스트를 실행하며 Simulator/Emulator는 로컬에서 검증합니다.

한계: 명령 기록과 클라이언트의 미확인 요청은 디스크에 저장하지 않습니다. 앱을 재시작하면 미확인 요청 ID를 잃습니다. 서버 재시작 후 404가 반환되면 실행 여부를 복원할 수 없어 앱은 계속 차단합니다. 서버 revision도 초기화되므로 개발 서버를 초기화할 때 앱 세션도 새로 시작해야 합니다. 이 Mock은 고정된 차량 10대를 대상으로 하며 삭제·추가나 서버 세대 전환을 처리하지 않습니다. 운영 환경의 영속 중복 방지, 인증·권한, 부하 한도, 실제 차량 연결은 범위 밖입니다.

플랫폼별 실행 결과는 [검증 기록](../remote-data.md)에 별도로 기록합니다.
